## 3. データ耐久性・可用性に関する禁止事項

「速くするため」「負荷を下げるため」であっても、以下のような変更は**提案も実行もしてはならない**。これらは障害時にデータを失わせたり、サービスを止めたりする原因になる。

### 3.1 データ耐久性を下げる変更の例

- データベースの同期書き込みの無効化・緩和
  - 例: PostgreSQL の `fsync = off`、`synchronous_commit = off`、`full_page_writes = off`
  - 例: MySQL の `innodb_flush_log_at_trx_commit` を `0` や `2` にする、`sync_binlog = 0`
  - 例: Redis の永続化(AOF / RDB)の無効化や `appendfsync` の緩和
- WAL / トランザクションログ / ジャーナルの無効化・縮小
- ファイルシステムのジャーナリング無効化、`nobarrier` 等の危険なマウントオプション
- 永続データを `tmpfs` やメモリ上に置く変更
- ディスクの書き込みキャッシュを危険な設定にする変更
- バックアップの停止・頻度削減・保持期間の短縮

### 3.2 可用性を下げる変更の例

- レプリカ数・冗長構成の削減(レプリケーション係数を下げる、スタンバイを止める等)
- 同期レプリケーションから非同期への切り替え
- ヘルスチェック、監視、アラートの無効化
- タイムアウト、リトライ、サーキットブレーカー、レート制限の削除
- ログ出力の停止(障害調査ができなくなる)
- 単一障害点を生む構成変更

パフォーマンスに問題がある場合は、上記のような手段ではなく、**調査結果を人間に報告し、正規の手順で対策を検討すること。**

## 5. 変更が必要な場合の正しい手順

調査の結果、修正や設定変更が必要だと判断した場合は、**サーバー上では何も変更せず**、以下の流れに従う。

1. 調査結果(何が起きているか、根拠となるログやメトリクス、推定原因)を人間に報告する
2. 修正案を提示する(コード差分や設定変更案は**提案として**示し、サーバー上には書き込まない)
3. 修正は、サーバーとは別の開発環境で、リポジトリのブランチ上で行う
4. プルリクエストを作成し、人間によるレビューを受ける
5. CI でテストを通す
6. 承認済みのデプロイパイプラインを通じて本番に反映する
